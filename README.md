# Paper Reader · 论文双语阅读器

导入 PDF 论文 → 版面感知切片 → 逐段流式翻译 → **一段英文一段中文**的极简阅读器。
整包 Docker 化，一条命令启动，数据落在本地 `./data`。

```
┌── 书库 ────────────────┐   ┌── 阅读器 ──────────────────────┐
│ 拖入 PDF               │ → │ Sparse attention has a long... │  ← 英文原文（弱化灰阶）
│ 自动切片 25 段         │   │ 稀疏注意力在高效序列建模中有着 │  ← 中文译文（逐段流入）
│ 进度 72%               │   │ …                              │
└────────────────────────┘   └────────────────────────────────┘
```

> **当前本机部署状态**：容器 `paper-reader` 已在跑，访问 **http://localhost:8010**
> （宿主机 8000 已被 `enso-crop-intel` 占用，故 `.env` 中 `HOST_PORT=8010`；改这个值即可换端口）。
> 模型为 DeepSeek `deepseek-chat`，书库里那篇 `sample_paper.pdf` 是自带样例，可直接点「阅读」看双语效果，不需要时点 ✕ 删除。

## 快速开始（Docker，推荐）

```bash
cd paper-reader
cp .env.example .env          # 填入 LLM_API_KEY
docker compose up -d --build
open http://localhost:8000
```

只想先看效果、不配置模型？把 `.env` 里的 `LLM_MOCK=1` 打开即可跑通全流程（输出假译文，不产生费用）。

常用命令：

```bash
docker compose logs -f          # 看日志
docker compose down             # 停止
docker compose up -d --build    # 改代码后重建
```

> 国内网络若 pip 拉取慢，取消 `docker-compose.yml` 中 `PIP_INDEX_URL` 的注释改用清华源。

## 配置项（`.env`）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `LLM_API_KEY` | 空 | 任意 OpenAI 兼容服务的 Key（DeepSeek / OpenAI / Kimi / 硅基流动…） |
| `LLM_BASE_URL` | `https://api.deepseek.com/v1` | 接口地址，Ollama 可填 `http://host.docker.internal:11434/v1` |
| `LLM_MODEL` | `deepseek-chat` | 模型名 |

| `LLM_CONCURRENCY` | `6` | 段落级并发，过高易触发限流 |
| `LLM_MOCK` | `0` | `1` = 模拟模式，不调用真实模型 |

| `MAX_UPLOAD_MB` | `80` | 上传大小上限 |
| `HOST_PORT` | `8000` | 宿主机端口 |

Key 改了但容器没重启 → 右上角「温度/模型」状态栏会提示未配置模型。

## 它是怎么做切片的

论文 PDF 直接抽文本会得到「一锅乱炖」，本项目做了 5 件事：

1. **双栏阅读顺序还原**：把页面横向切成 200 个格子做占用直方图，只让「窄块」参与统计，
   在页面中部找最长空白沟（gutter）判定双栏；再用「整幅宽块（标题/摘要/跨栏图表）作为分隔带」，
   在每个带内先读左栏再读右栏。首页「整幅标题+摘要 + 下方双栏正文」这种常见版面也能正确处理。
2. **页眉页脚过滤**：位于上下 7.5% 边距、且跨页重复或形如页码的文本块直接丢弃；竖排页边横幅（arXiv 水印）按方向角过滤。
3. **段落合并**：跨行、跨块、跨栏、跨页的断段，按「行间距 + 断句标点 + 字号一致性」三类信号合并；
   行尾连字符（`atten-` + `tion`）自动接回。
4. **内容识别**：标题、章节标题（含 `3.1` 多级编号）、图注、首页作者单位、参考文献分区分别打标；
   参考文献在阅读器中默认折叠，且默认不送翻译。
5. **公式保护**：整段以公式/代码为主的块标记为 `keep`，原样保留不翻译；行内公式、引用
   `[3]`、`(Vaswani et al., 2017)`、`O(n^2)`、`Figure 2`、`Table 1`、代码标识符等在翻译前
   统一挖空成 `[[0]]` 占位符，翻译后按序还原——模型无法篡改公式与引用（还原失败会自动重试）。

可以用样例自检：

```bash
python tools/make_sample_pdf.py tools/out/sample_paper.pdf   # 生成双栏样例论文
python tools/smoke_test.py                                   # 打印切片结果并做断言
```

## 朗读（小米 MiMo TTS）

阅读器右上角 ▶ 从当前可见位置开始**逐段朗读中文译文**，再点一次停止（快捷键 `p`）；
鼠标移到任意段落上点 🔈 只读这一段。朗读中的段落会高亮并自动滚到屏幕中间，
下一段音频会在当前段播放时提前合成，衔接不断档。

- 接口：`mimo-v2.5-tts`，文本走 `assistant` 消息、音频以 base64 返回（OpenAI 兼容的 chat/completions）；
- 音色：`mimo_default`（默认）以及 冰糖 / 茉莉 / 苏打 / 白桦 / Mia / Chloe / Milo / Dean，可在 ⋯ 菜单里切换；
- **磁盘缓存**：同模型同音色下的同一段文本只合成一次（`data/tts/*.wav`），重听、刷新、二次打开都不再计费；
- 朗读前会自动清洗文本：去掉 `[[0]]` 占位符、`[3]` 这类引用编号、LaTeX 残片与图表编号，符号转成中文读法（`→` 读作"到"、`%` 读作"百分之"）；
- 长段落按句子切成多次请求再拼接 WAV，避免单次过长影响音质。

### 语音播放器

播放时阅读器底部会出现播放条，功能齐全：

| 控件 | 作用 |
| --- | --- |
| ⏮ / ⏭ | 上一段 / 下一段译文 |
| **−3s / +3s** | **后退 3 秒 / 快进 3 秒**，可连按累加（实测 +3.00 s、连按三次 +9.00 s） |
| ▶ / ❚❚ | 播放 / 暂停 |
| 进度条 | 显示当前段进度，**点击或拖动可任意跳转** |
| 时间 | `当前 / 总时长`（如 `0:09 / 0:18`） |
| 语速 | 0.75× / 1× / 1.25× / 1.5× / 2× |
| ✕ | 关闭播放器 |

键盘：`空格` 播放/暂停，`→` 快进 3 秒，`←` 后退 3 秒，`p` 开始/暂停朗读。
播放中的段落会高亮；只有当该段滚出视野时才自动跟随滚动，不会打断你翻看别处的阅读。

### 段落衔接为什么会有延迟，以及怎么解决的

先用同一批文本直接压测了 MiMo 接口（结论：**接口不慢，也没有并发限制**）：

| 文本长度 | 单次合成耗时 |
| --- | --- |
| 38 字 | 2.3 s |
| 180 字 | 6.5 s |
| 420 字 | 21.1 s |
| **6 路并发同一段** | 6.7–8.8 s **全部返回，零限流** |

问题出在客户端逻辑：

1. **预合成是严格串行的**（一次只合成一段）。章节标题的音频只有 1.4 秒，而它后面那段正文
   要 6–20 秒才合成完，串行根本追不上 → 每次"标题 → 正文"的边界必然静音 5–20 秒；
2. **一暂停就永久停掉预合成**（旧实现用 `player.playing` 做循环条件，且没有恢复入口）；
3. **长段落整段一次请求**，21 秒才回来，而接口明明支持并发。

现在的做法：

- **并行调度器**：3 路并发、最近优先（永远先备第 pos+1 段），播放位置前进后自动续排；
- **长段落分片并行合成**（`TTS_CHUNK_CHARS=180`）：420 字的段落切成 3 片同时请求，
  墙钟时间从 21 秒降到约 7 秒，再在服务端拼回一个 WAV；
- **服务端全局限流 + 重试**（`TTS_CONCURRENCY=4`，429/5xx 自动退避重试 2 次）；
- 暂停/恢复都不影响调度：暂停时不排新任务，已在飞的请求会完成并入库（钱已经花了，不浪费）；
- **等待可见**：播放条显示`正在合成 8s…`和`已备好后续 9 段`，不再是"看着像卡死"。

实测（一篇全新未合成过的论文，故意每段一出声就跳到结尾以制造零缓冲的最坏情况）：

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 段落切换空档 | 5–20 秒 | 平均 **0.7 秒**，最大 4.3 秒 |
| 正常听时的缓冲 | 1 段 | **16 秒内把剩余 9 段全部备好**（29 MB 音频） |
| 合成失败 | 静默跳过 | 弹浮层提示"第 N 段合成失败，已跳过" |

队列播完时若又有新译好的段落会自动续接；停止朗读会终止后续排程。

朗读文本还会自动清洗：邮箱与网址、`(Section 3.2)` 这类交叉引用、`通讯作者：…` 联系方式、
`[[0]]` 占位符、引用编号都去掉，`12.5%` 改写成"百分之12.5"（中文语序），
`→` 读作"到"。清洗规则变化会自动换缓存键，旧音频不会串用。

实测（样例论文 262 字的一段）：首次合成 **11.2 s → 48.8 s 音频**（24 kHz / 16 bit / 单声道），
二次请求 **0.03 s 命中缓存**。TTS 对本地算力零占用，全程走云端。

`.env` 里对应的配置项：`TTS_API_KEY` / `TTS_BASE_URL` / `TTS_MODEL` / `TTS_VOICE` / `TTS_FORMAT`。
把 `TTS_API_KEY` 留空即隐藏朗读按钮。

### 退出即清理语音缓存

朗读音频按段落缓存在 `data/tts/`（重听、拖进度条、快进 3 秒都不再计费），代价是占磁盘
（实测一篇论文听下来约 50 MB）。默认开启「退出即清理」，覆盖**三条真实退出路径**：

| 退出方式 | 触发机制 | 清理范围 |
| --- | --- | --- |
| **返回书库**（左上角 ←） | 路由切换 | 刚读的这篇，并弹出浮层提示"释放 X MB" |
| **关闭标签页 / 关闭浏览器 / 离开页面** | `pagehide` + `navigator.sendBeacon` | 刚读的这篇 |
| **服务停止**（`docker compose stop/down/restart`） | 应用关闭钩子 | 全部（日志会记 `服务退出，已清理语音缓存：释放 X MB`） |

删除文档（书库里的 ✕）也会连带清掉该篇音频。

**刻意没做的事**：不监听 `visibilitychange`——切到别的标签页不算退出，而"边听边干别的"是常见用法，
那时清理会导致切回来重新合成、白花钱。

提示是右下角浮层（不是一闪而过的小字），会显示释放的磁盘空间、哪篇论文，
并提醒"下次朗读会重新合成，可在 ⋯ 菜单关闭此行为"，7 秒后自动消失，也可点 ✕ 关闭。

`⋯` 菜单里的手动入口：**清理本篇语音缓存**（显示 `本篇 48.2 MB / 全部 124.4 MB`）、
**清空全部语音缓存**。关掉自动清理开关则长期保留——**注意：清理过的段落下次朗读会重新合成并重新计费**。
命令行等价操作：`make clean-tts`。

另有一份**翻译缓存**（`GET/DELETE /api/cache`，`make clean-cache`）：它跟文档分开存储、全局共享，
删文档不会影响它——重新导入同一篇论文时，已译段落依然命中缓存，不会重新花翻译费。

## 本地模型（可选，当前权重已清理）

默认配置用云端 DeepSeek。若想完全本地跑（零 token 费用、断网可用），用 Ollama + Qwen3-1.7B Q4_K_M：

```bash
mkdir -p /Users/Zhuanz1/Desktop/models/llm && cd /Users/Zhuanz1/Desktop/models/llm
curl -L -o Qwen3-1.7B-Q4_K_M.gguf \
  "https://hf-mirror.com/unsloth/Qwen3-1.7B-GGUF/resolve/main/Qwen3-1.7B-Q4_K_M.gguf"
ollama create qwen3-1.7b-zh -f /path/to/Modelfile.qwen3   # 见 scripts/serve_local_llm.sh 头部
cd /Users/Zhuanz1/Desktop/paper-reader
nohup ./scripts/serve_local_llm.sh > /tmp/local-llm.log 2>&1 &
make use-local
```

**实测数据**（MacBook Air 13" M3 / 8 GB，无风扇）：

| 指标 | 数值 |
| --- | --- |
| 模型体积 / 常驻内存 | 1056 MB / 约 1.9 GB（100% Metal GPU） |
| 单段翻译耗时 | 平均 1.4 s（首段含预填充 5.5 s） |
| 整篇 18 段 | 29 s |
| 电池温度变化 | 30.82 → 30.86 °C（**+0.04 °C**） |

**无风扇机器的散热策略**（都已内置）：

- `num_thread 3`：只用 3 个性能核，留一核给系统；
- `num_batch 128`：压低预填充瞬时功耗峰值；
- 模板预置空 `think` 块：关掉 Qwen3 思考链，否则每段先吐几百 token 纯烧 CPU；
- `LLM_REQUEST_INTERVAL=1.5`：每段之间强制间隔，把 CPU 占空比压到约 60%；
- `OLLAMA_KEEP_ALIVE=2m`：空闲 2 分钟卸载模型，待机不积热；
- KV 缓存 `q8_0` + flash attention：4096 上下文省约一半缓存内存。

想更凉快：把 `LLM_REQUEST_INTERVAL` 调到 3–5，并把 `PARAMETER num_thread` 降到 2；代价是整篇翻译时间成比例变长。

## 阅读器

- **双语模式**：英文原文在上（衬线体、灰阶弱化），中文译文在下（正文字号、行高 1.86），段落成对呈现；
- **仅中文 / 仅英文** 一键切换，适合快速浏览与对照原文；
- 翻译**逐段流式出现**：不必等整篇译完，打开即读；悬浮段落可单段重译、复制原文；
- 顶部细进度条显示翻译进度；`⋯` 菜单可继续翻译、忽略缓存重译全文、导出双语 Markdown、切换省流量模式；
- **省流量模式**：只翻译滚动到的可见段落（按需请求），适合只精读某几节；
- 快捷键：`m` 切换显示模式、`t` 深浅色、`j/k` 上下滚动、`Esc` 返回书库；
- 内置术语表（60+ AI 领域词条）可在线增删改，命中即强制统一译法；
- 原文 PDF 一键回看，译文可导出为 Markdown。

## 缓存与花费

段落级缓存：同一段落（同模型 + 同术语表 + 同提示词版本）只翻译一次，
重复导入同一篇论文、或两篇论文有相同段落时直接命中本地缓存，**不再消耗 token**。
缓存保存在 `./data/paper_reader.db`，删掉该文件即可全部重置。
界面 `用量` 面板可查看请求数、输入/输出 token 与缓存条目数。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/docs` | 上传 PDF，返回解析后的段落块 |
| `GET` | `/api/docs` | 文档列表（含翻译进度） |
| `GET` | `/api/docs/{id}` | 文档详情 + 全部段落 |
| `GET` | `/api/docs/{id}/translate` | **SSE 流式翻译**，`?idx=1,2,3` 指定段落，`?force=1` 忽略缓存 |
| `POST` | `/api/docs/{id}/blocks/{idx}/translate` | 单段翻译（省流量模式用） |
| `GET` | `/api/docs/{id}/file` | 原始 PDF |
| `GET` | `/api/docs/{id}/export.md` | 导出双语 Markdown |
| `POST` | `/api/docs/{id}/reset` | 清空译文（`?keep_done=true` 只重置失败/未译段落） |
| `GET/POST/DELETE` | `/api/glossary` | 术语表增删改查 |
| `GET` | `/api/stats` | 用量统计 |

SSE 事件：`meta`（总数/模型）→ `block`（`{idx, zh, status, cached?}`，逐条到达，顺序不保证，前端按 `idx` 归位）→ `done`（汇总与进度）。

## 已知边界

- 扫描版（图片型）PDF 无法提取文本，接口会明确报错，请先做 OCR；
- 表格内部结构与多行公式的还原依赖 PyMuPDF 文本层，复杂公式会以 `keep` 原样保留而不翻译；
- 每段一次请求以保证「逐段流入」的阅读体验，段落极多（>500）时建议用省流量模式；
- 译文质量取决于所选模型，术语一致性问题可通过术语表在线修正后重译。
